SECTION 3: EXISTING APPLICATION DEPENDENCIES
============================================================

The following dependencies are verified from repository source queries and
the supplied schema. File names identify dependency surfaces; this is not an
exhaustive call graph.

DATABASE CONNECTION
- db.php defines the Database singleton and exposes mysqli connections.
- includes/bootstrap.php, includes/system_guard.php and license guards are
    loaded by application areas that require authenticated or licensed access.
- The connection is configured for utf8mb4.

IDENTITY AND ACCESS
- login.php and the admin/teacher/student areas use session IDs and roles.
- admins, teachers and super_admins are separate identity tables in the
    supplied schema. Their cross-table relationships are not declared.
- teachers are connected to subjects by teacher_subjects.subject, a text
    value, and to classes by teacher_classes.

CLASSES, STUDENTS AND SUBJECTS
- admin/manage_classes.php and student-management pages use classes,
    streams, academic_levels and students.
- students.class is a required VARCHAR value, while classes is a separate
    normalized table. The supplied schema does not connect students.class to
    classes.id.
- subjects is keyed by subject_name. teacher_subjects.subject and several
    test fields also store subject names rather than subject_id values.
- subject_levels.class_level is a fixed PRIMARY/JSS/SS ENUM.

TESTS, QUESTIONS AND ATTEMPTS
- admin/manage_test.php, teacher/manage_test.php, teacher/add_question.php,
    teacher/bank.php and related pages use tests, new_questions, question_bank
    and the question-type detail tables.
- tests is filtered by academic_level_id and subject; it has no teacher_id or
    stream_id in the supplied schema.
- student/take_exam.php and student/save_answer.php use exam_attempts.
    The unique key is (user_id, test_id, question_id), so one logical attempt
    is represented by multiple question rows rather than by a separate
    attempt header in the supplied schema.
- results joins user_id to students.id in teacher/admin result pages, but the
    supplied schema declares no foreign key for results.user_id.
- The question detail tables cascade from new_questions. tests deletion can
    cascade to question_bank, results and exam_attempts according to the
    supplied foreign keys, which is a historical-data risk.

SCHEDULING, RECORDS AND REPORTING
- admin/exam_schedule.php reads subjects and writes/reads the active exam
    scheduling surface. active_exams is the only supplied schedule-like table.
- admin/manage_session.php and teacher/add_question.php use academic_years.
- student_subject_scores and student_term_remarks support school report
    records; the schema comment calls academic_year_id a term even though the
    table is named academic_years.
- Teacher/admin result views join results, students, tests, academic_levels
    and sometimes classes for filtering and exports.

BACKUPS, AUDIT AND LICENSING
- backup/backup_functions.php, backup/config.php and backup pages use
    backups, backup_settings and admins. mysqldump includes routines, triggers
    and events, so later schema changes must preserve backup/restore testing.
- includes/audit.php and admin audit pages use audit_logs; the supplied
    schema also contains activities_log, creating two logging surfaces.
- license/helpers.php and license/verify.php read and write licenses. The
    current local identity is represented by school_name, machine_fingerprint,
    installation_id and signatures; no institution foreign key exists.

VERIFIED DISCREPANCIES REQUIRING INVESTIGATION
- admin/download.php contains a query for tests.class, but tests.class is
    absent from the supplied CREATE TABLE definition. This path may be stale,
    may depend on an unrecorded live column, or may be broken.
- teacher/get-results-details.php queries exam_results, but exam_results is
    absent from the supplied schema. This path may be legacy or broken.
- Some pages use academic_levels.level_code as the class source of truth,
    while other code accepts class text or attempts to use classes.class_name.
- The repository contains no independently located migration/schema file in
    the reviewed source set. The live database, if available, must be compared
    using SHOW CREATE TABLE and INFORMATION_SCHEMA before implementation.

SECTION 4: CURRENT ARCHITECTURAL LIMITATIONS
============================================================

1. Institution isolation is not modeled. schools exists, but no supplied
     foreign keys connect it to students, teachers, classes, subjects, tests,
     results or licenses. The current design therefore does not provide a
     verified multi-institution tenant boundary.
2. academic_levels.class_group and subject_levels.class_level hardcode
     Nigerian/primary categories. They cannot represent Year 10, Grade 8,
     freshman, doctoral study, a corporate team or a certification cohort.
3. Class identity is duplicated as students.class, classes.class_name,
     academic_levels.level_code and tests.academic_level_id. These values can
     disagree and historical meaning depends on application conventions.
4. Subjects are duplicated as names in subjects, teacher_subjects and tests.
     Renaming, localization, course codes and cross-programme offerings are
     therefore difficult to enforce safely.
5. Academic years combine year/session/exam-title data and are also used as
     a term in student_subject_scores. Periods and assessment events are not
     clearly separated.
6. Results and attempts identify users with unverified integer conventions;
     no declared candidate/person foreign key protects referential integrity.
7. An assessment targets an academic level directly. There is no separate
     target, eligibility, scheduled sitting or attempt-header abstraction for
     institution-wide, cross-unit or selected-candidate assessments.
8. Separate identity tables make employees, candidates, administrators and
     learners difficult to model consistently or assign to multiple units.
9. The question model is useful for preserving current functionality, but
     each type has a separate table and answer storage is text/boolean. Any
     universal extension must avoid breaking existing question IDs and scoring.
10. Cascade rules on tests and questions can remove historical results or
        question records. Deletion policy needs explicit archival rules.

SECTION 5: PROPOSED UNIVERSAL ARCHITECTURE
============================================================

All designs in Sections 5-10 are PROPOSED - NOT YET IMPLEMENTED.

The central rule is to keep five concepts separate:

PERSON AND IDENTITY: one person/candidate identity can have institutional
roles, credentials and more than one membership.

ORGANIZATION: an institution owns configurable unit types and units. An
institution may have no department, faculty, class or academic level.

ACADEMIC OR PROFESSIONAL CLASSIFICATION: periods, levels, programmes,
qualifications, courses and subjects describe learning context. They are not
the same as an organizational reporting line.

MEMBERSHIP: a person may belong to multiple units, programmes, cohorts or
teams with effective dates and a role. Membership must be separate from the
unit table so cross-department courses and joint programmes do not require
duplicating a person.

ASSESSMENT ELIGIBILITY: an assessment may target an institution, one or more
units, a programme, level, course, explicit assessment group or individual
candidate. Eligibility must be evaluated independently of the organization
tree and recorded for the scheduled sitting where necessary.

ILLUSTRATIVE CONFIGURATIONS

Nigerian secondary school:
    Institution -> Secondary School -> SS2
    SS2 may be an organizational unit, an academic level, or both through an
    explicit mapping; the design must not force that choice globally.

UK secondary school:
    Institution -> Secondary School -> Year 10

Nigerian university:
    Institution -> Faculty -> Department -> Programme -> Level

American university:
    Institution -> College -> Department; academic classification is a
    separate year/freshman-sophomore model.

Corporate organization:
    Organization -> Division -> Department -> Team
    An assessment can target several teams without creating a new hierarchy.

LIMITS OF A PURE TREE

organizational_units.parent_id supports a convenient hierarchy, but a tree
cannot represent all affiliations. Cross-listed courses, joint programmes,
matrix reporting and temporary project teams require separate membership,
course-offering and assessment-target relations. Parent links should permit
NULL, and units should be deactivated rather than deleted when history uses
them.

ASSESSMENT LIFECYCLE

Assessment definition -> assessment targets/eligibility -> scheduled session
-> candidate attempt -> response/scoring -> result/review/history.

The current tests, question_bank, new_questions, question detail tables,
exam_attempts and results should be adapted incrementally around this
lifecycle. They should not be duplicated for each institution type.

SECTION 6: PROPOSED DATABASE SCHEMA
============================================================

Every item below is PROPOSED - NOT YET IMPLEMENTED. Types are indicative and
must follow the existing MySQL/MariaDB version and naming conventions.

institution_types: configurable category such as school, university,
corporate or training provider. Proposed fields: id BIGINT/INT PK, code
VARCHAR(50) UNIQUE, name VARCHAR(150), description TEXT, is_active TINYINT,
created_at DATETIME. Optional; institution records may use a generic type.

institutions: tenant and institutional identity. Proposed fields: id PK,
institution_type_id FK, name VARCHAR(255), code VARCHAR(100) UNIQUE within
the deployment, timezone VARCHAR(64), locale VARCHAR(16), status,
created_at, updated_at. Every future tenant-owned record should ultimately
have institution_id, with indexes and foreign keys enforcing isolation.

organizational_unit_types: institution-configurable labels such as Faculty,
Class, Division or Team. Proposed fields: id PK, institution_id FK nullable
only if globally reusable, name, code, parent_allowed, is_active, UNIQUE
(institution_id, code).

organizational_units: configurable units. Proposed fields: id PK,
institution_id FK, unit_type_id FK, parent_id FK to organizational_units
nullable, name, code, status, valid_from, valid_to, created_at, updated_at.
Indexes: (institution_id, parent_id), (institution_id, unit_type_id), and a
unique active/business code per institution where appropriate. Do not assume
all units need a parent.

people: shared person/candidate record. Proposed fields: id PK,
institution_id FK where deployment isolation requires it, external_reference,
given_name, family_name, display_name, email, phone, status, created_at,
updated_at. A separate account/role relation should be considered before
merging authentication into people. Existing students and teachers must be
mapped without losing IDs.

organizational_unit_members: many-to-many membership. Proposed fields: id PK,
institution_id FK, person_id FK, organizational_unit_id FK, membership_role,
is_primary, valid_from, valid_to, status, UNIQUE(person_id, unit_id,
valid_from). Index person and unit lookups. Historical memberships must not
be overwritten.

academic_periods: institution-owned sessions, terms, semesters or cohorts.
Proposed fields: id PK, institution_id FK, parent_period_id nullable,
period_type, name, starts_at, ends_at, status, UNIQUE(institution_id, name).
This replaces neither academic_years nor historical rows until migration is
validated.

academic_levels: evolve the existing concept with institution_id, name,
code, level_type, sequence_number and optional parent/programme links. Keep
legacy level IDs and level_code during transition; remove fixed ENUMs only in
a later migration.

programmes and courses: optional institution-owned academic/professional
catalog records. A programme may reference a qualification and units; a
course may be offered to multiple programmes through a course_offerings
relation. Existing subjects remain valid for simple school deployments.

subjects: retain the current table initially, then add institution ownership,
stable code and optional course/catalog links. Replace text joins only after
all callers can use subject_id.

assessment_groups: named candidate cohorts or eligibility sets. Proposed
fields: id PK, institution_id FK, name, group_type, period_id nullable,
created_at, status. A separate assessment_group_members table should support
explicit people; rule/target tables may support dynamic groups.

assessment_assignments: links an assessment to a person, group, unit,
programme, level, course or institution. Proposed fields: id PK,
assessment_id FK to the eventual assessment definition, target_type,
target_id, group_id nullable, period_id nullable, availability/status,
created_at. Add uniqueness preventing duplicate active targets and indexes by
assessment, institution and target. This is the main decoupling from classes.

ASSESSMENT ENGINE CHANGES

The existing tests table can initially act as the assessment definition. Add
an adapter or nullable universal identifiers before considering a rename.
Create a distinct scheduled-session concept only when current scheduling
requirements are mapped. Create an attempt header only if it solves the
current per-question attempt limitation; retain existing exam_attempts rows
as response history. Results should gain explicit candidate/assessment/session
references while preserving test_id and user_id during the transition.

SECTION 7: EXISTING VS PROPOSED SCHEMA
============================================================

EXISTING: schools, school_name only.
CURRENT PURPOSE: one school-name record, with no verified ownership links.
PROPOSED CHANGE: institutions plus institution_types and tenant keys.
REASON: support schools, universities and companies with isolation.
IMPACT: every dependent table and license lookup needs staged mapping.

EXISTING: academic_levels.class_group ENUM('JSS','SS').
CURRENT PURPOSE: secondary-school level classification.
PROPOSED CHANGE: configurable level type/code per institution; preserve the
legacy value in a compatibility mapping.
REASON: support Year, Grade, university level and non-academic structures.
IMPACT: class filters, tests, reports and subject-level queries.

EXISTING: classes, streams, teacher_classes and students.class.
CURRENT PURPOSE: school classes and teacher assignments.
PROPOSED CHANGE: map classes to organizational_units and move membership to
organizational_unit_members while retaining legacy IDs.
REASON: support arbitrary units and multiple memberships.
IMPACT: student, teacher, result and export queries.

EXISTING: subjects, subject_levels, teacher_subjects.subject and tests.subject.
CURRENT PURPOSE: subject catalog and text-based assignment/filtering.
PROPOSED CHANGE: add institution scope and stable subject/course references;
retain text values during a compatibility period.
REASON: avoid name collisions and support international catalogues.
IMPACT: teacher permissions, tests, schedules and reports.

EXISTING: academic_years and tests.year.
CURRENT PURPOSE: school sessions and test labels.
PROPOSED CHANGE: academic_periods plus explicit assessment/session dates.
REASON: separate year, term, semester, cohort and exam event.
IMPACT: reports and historical filters.

EXISTING: tests, question_bank, new_questions, type tables.
CURRENT PURPOSE: assessment definitions and question composition.
PROPOSED CHANGE: preserve engine; add universal assessment identity and
assignment/target relations.
REASON: target individuals, groups, units or institutions without cloning
question data.
IMPACT: low initially, but assignment and scheduling code must be adapted.

EXISTING: exam_attempts and results.
CURRENT PURPOSE: per-question answers and scored test results.
PROPOSED CHANGE: add explicit candidate, assessment, session and result
version references; preserve test_id/user_id as legacy links.
REASON: distinguish attempt, response, score and historical result.
IMPACT: scoring, reattempts, exports and deletion policies.

EXISTING: licenses.school_name.
CURRENT PURPOSE: local license identity and activation.
PROPOSED CHANGE: optional institution_id after a stable mapping exists;
retain school_name for old licenses.
REASON: support product editions and institution types without breaking
offline activation. Licensing implementation is unchanged in this phase.

EXISTING: audit_logs, activities_log, backups, backup_settings.
CURRENT PURPOSE: operational history and database backup metadata.
PROPOSED CHANGE: add tenant context only after isolation rules are approved;
preserve audit and backup history.
REASON: trace universal operations and retain offline recoverability.

SECTION 8: MIGRATION AND BACKWARD COMPATIBILITY
============================================================

Phase 0 - discovery: take a verified backup; capture SHOW CREATE TABLE,
INFORMATION_SCHEMA constraints/indexes, row counts and representative
relationships. Inventory every query that uses legacy columns, including
tests.class and exam_results, and decide whether those paths are stale.

Phase 1 - additive foundation: add new tables and nullable mapping columns
only. Do not drop or rename legacy tables. Create an explicit mapping from
schools to institutions, JSS/SS levels and existing classes to units.

Phase 2 - dual reads/controlled writes: continue writing legacy values while
writing mapped universal records in the same local transaction where
possible. Use feature flags and log unmapped records. Existing IDs remain
stable; no historical test, question, attempt or result is recreated with a
new ID unless an auditable mapping is stored.

Phase 3 - backfill and validate: map students, teachers, subjects, teacher
assignments, academic years and classes. Compare counts, nulls, duplicates,
subject names, test targets, result totals and attempt totals. Validate
reports against pre-migration exports.

Phase 4 - staged cutover: enable universal assignment and membership flows
for a pilot institution while preserving legacy result and exam paths. Keep
legacy columns readable until all supported flows pass offline tests.

Rollback: restore the pre-migration backup or reverse only additive mappings,
disable feature flags, and return reads to legacy tables. Never rollback by
deleting shared historical rows. Test restore using the existing mysqldump
workflow before production use.

Backward-compatibility rules: preserve JSS/SS labels, class names, student
and teacher identifiers, subject names, test/question IDs, attempts, results,
academic-year rows and license records. Use soft deactivation for units and
catalog data referenced by history.

SECTION 9: IMPLEMENTATION ROADMAP
============================================================

1. Universal database foundation. Add mapping tables, institution scope and
     integrity documentation. Acceptance: no legacy row loses identity and all
     existing offline workflows pass regression tests.
2. Dynamic organizational units. Implement configurable unit types, nullable
     parent links, deactivation and membership. Acceptance: JS/SS classes can
     be mapped and a non-school hierarchy can be represented.
3. Institution onboarding/templates. Provide optional school, university,
     training and corporate templates without making them mandatory. Acceptance:
     a new institution can configure names and depth locally offline.
4. People and memberships. Unify candidate/learner/employee references while
     retaining old student/teacher accounts. Acceptance: one person can hold
     multiple current memberships with history.
5. Universal assessment assignment. Add targets, groups and scheduled
     sessions around the existing tests engine. Acceptance: individual,
     multi-unit, programme, level, group and institution targets work offline.
6. University and college support. Add programmes, courses, offerings,
     levels and qualifications only where needed. Acceptance: courses can span
     departments without duplicating candidates or questions.
7. Corporate assessment support. Support divisions, teams, recruitment and
     competency classifications using the same target model. Acceptance: an
     assessment can span teams and produce auditable results.
8. Internationalization. Add locale, timezone, terminology and configurable
     grading/period conventions. Acceptance: no fixed JSS/SS or country-specific
     value is required for a new institution.
9. Migration verification and stabilization. Run restore, offline, security,
     performance and report comparisons. Acceptance: rollback is documented,
     legacy history is readable, and unresolved data exceptions are zero or
     explicitly approved.

============================================================
SECTION 10: RISKS AND DESIGN DECISIONS
============================================================

- Schema abstraction can become harder to query than the current simple
    school model. Prefer additive, purpose-specific relations over a universal
    key-value table.
- Tenant isolation must be enforced by foreign keys, application checks and
    indexed institution scope; a name field such as school_name is insufficient.
- Flexible trees do not replace memberships, course offerings or assessment
    targets. Keep those relations separate.
- Existing cascade rules and stale query paths can destroy or hide history.
    Deletion and archival policy requires approval before migration.
- Offline operation means all structure, membership, assessment and result
    decisions must be locally available. Licensing and synchronization must not
    become runtime prerequisites.
- Adding institution_id to every table has performance and migration cost;
    the required tenant boundary must be approved before broad alteration.
- Authentication consolidation could affect roles and licensing. Do not merge
    admins, teachers, super_admins and students until access behavior is mapped.
- Grading, terminology, date formats, privacy retention and assessment
    integrity vary by institution and country; they must be configuration, not
    hardcoded universal assumptions.

CREATE TABLE IF NOT EXISTS organizational_units (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    institution_id INT NOT NULL,
    unit_type_id INT NOT NULL,
    parent_unit_id BIGINT NULL,
    unit_code VARCHAR(100) NULL,
    unit_name VARCHAR(255) NOT NULL,
    description TEXT NULL,
    sort_order INT NOT NULL DEFAULT 0,
    status ENUM('active','inactive','archived')
        NOT NULL DEFAULT 'active',
    legacy_class_id INT NULL UNIQUE,
    metadata JSON NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_org_institution_parent
        (institution_id, parent_unit_id),
    INDEX idx_org_unit_type (unit_type_id),
    UNIQUE (institution_id, unit_code),
    FOREIGN KEY (institution_id)
        REFERENCES institutions(id),

    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    UNIQUE (student_id, academic_year_id),
    FOREIGN KEY (student_id)
        REFERENCES students(id)
        ON DELETE CASCADE,
    FOREIGN KEY (academic_year_id)
        REFERENCES academic_years(id),
    FOREIGN KEY (teacher_id)
        REFERENCES teachers(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
  COLLATE=utf8mb4_unicode_ci;

CREATE TABLE IF NOT EXISTS grade_scales (
    id INT AUTO_INCREMENT PRIMARY KEY,
    min_score TINYINT UNSIGNED NOT NULL,
    max_score TINYINT UNSIGNED NOT NULL,
    grade CHAR(1) NOT NULL,
    remark VARCHAR(50),
    UNIQUE (grade)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
  COLLATE=utf8mb4_unicode_ci;

-- ============================================================
-- SECTION 18: SYSTEM SETTINGS AND SETUP
-- ============================================================

CREATE TABLE IF NOT EXISTS settings (
    id INT AUTO_INCREMENT PRIMARY KEY,
    setting_name VARCHAR(100),
    setting_value TEXT
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
  COLLATE=utf8mb4_unicode_ci;

CREATE TABLE IF NOT EXISTS system_settings (
    id INT AUTO_INCREMENT PRIMARY KEY,
    setup_completed TINYINT(1) DEFAULT 0,
    setup_completed_at TIMESTAMP NULL,
    setup_by INT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
  COLLATE=utf8mb4_unicode_ci;

-- ============================================================
-- SECTION 19: LICENSING
-- ============================================================

CREATE TABLE IF NOT EXISTS licenses (
    id INT AUTO_INCREMENT PRIMARY KEY,
    license_key VARCHAR(255) NOT NULL UNIQUE,
    school_name VARCHAR(255),
    machine_fingerprint VARCHAR(255),
    installation_id VARCHAR(255),
    installation_signature VARCHAR(255),
    license_signature VARCHAR(1024) NULL,
    license_type VARCHAR(100),
    activation_date DATETIME,
    expiry_date DATETIME,
    status ENUM(
        'inactive',
        'active',
        'expired',
        'revoked'
    ) DEFAULT 'inactive',
    last_verified DATETIME,
    last_system_time DATETIME,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    institution_id INT NULL,
    INDEX idx_licenses_institution (institution_id),
    FOREIGN KEY (institution_id)
        REFERENCES institutions(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
  COLLATE=utf8mb4_unicode_ci;

-- ============================================================
-- SECTION 20: BACKUP MANAGEMENT
-- ============================================================

CREATE TABLE IF NOT EXISTS backups (
    id INT AUTO_INCREMENT PRIMARY KEY,
    filename VARCHAR(255) NOT NULL,
    backup_type ENUM('manual','automatic')
        DEFAULT 'manual',
    status ENUM('valid','corrupted')
        DEFAULT 'valid',
    file_size BIGINT NOT NULL,
    checksum VARCHAR(64),
    created_by INT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    restore_count INT DEFAULT 0,
    restored_at DATETIME NULL,
    FOREIGN KEY (created_by)
        REFERENCES admins(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
  COLLATE=utf8mb4_unicode_ci;

CREATE TABLE IF NOT EXISTS backup_settings (
    id INT AUTO_INCREMENT PRIMARY KEY,
    auto_backup_enabled TINYINT(1) NOT NULL DEFAULT 1,
    backup_frequency ENUM(
        'hourly',
        'daily',
        'weekly',
        'monthly'
    ) DEFAULT 'daily',
    backup_time TIME DEFAULT '00:00:00',
    retention_days INT DEFAULT 30,
    max_backups INT DEFAULT 50,
    last_backup DATETIME NULL,
    next_backup DATETIME NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
    ON UPDATE CURRENT_TIMESTAMP
);
